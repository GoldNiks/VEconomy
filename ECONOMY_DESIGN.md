# VEconomy — проектное решение

Этот документ фиксирует архитектурные решения ядра экономики. Он нужен, чтобы будущие
доработки (аукцион, обменники, FTB-интеграции) сохраняли целостность денежной системы.

## 1. Принципы

1. **Деньги — только целые.** Все суммы — `long` в минимальных единицах валюты
   («копейках»). `double`/`float` для денег запрещены. Это исключает ошибки округления
   и упрощает сверку.
2. **Единая точка изменения баланса.** Баланс меняется только через сервисы
   (`AccountService`, `TransferService`, `EscrowService`), которые всегда пишут журнал
   в той же транзакции. Прямые UPDATE по таблице `accounts` недопустимы.
3. **Атомарность и согласованность.** Изменение баланса + запись журнала — одна
   транзакция SQLite. Параллельные операции сериализуются через
   `DatabaseManager.inTransaction` (одно соединение), плюс optimistic locking через
   поле `version` таблицы `accounts`.
4. **Идемпотентность.** Любая операция может нести `idempotencyKey`; повтор с тем же
   ключом возвращает `DUPLICATE_OPERATION` и не меняет баланс. Это позволяет безопасно
   ретраить операции (начисление наград, внешние плагины).
5. **Неизменяемый журнал.** Таблица `transactions` — append-only. Административные
   корректировки фиксируются отдельным типом операции, а не правкой истории.

## 2. Модули

| Модуль | Отвечает за |
|---|---|
| `api/` | Публичные контракты `EconomyApi`, `EscrowApi`, типы и результаты |
| `config/` | Forge-конфиг + неизменяемый снимок `EconomySettings` |
| `persistence/` | SQLite: подключение, миграции, репозитории, legacy-импорт |
| `economy/` | Бизнес-логика: аккаунты, переводы, эскроу, журнал, казна, формат |
| `audit/` | Статистика для `/economy admin stats` |
| `command/` | Brigadier-команды |
| `event/` | Крючки Forge (старт/стоп БД, вход игрока) |
| `EconomyCore` | Composition root: инициализация, фасады, применяет настройки |

Сервисы держат ссылку на `EconomySettings` (volatile) и обновляют её через
`applySettings(...)` — так `/economy admin reload` применяет изменения без перезапуска.

## 3. Модель данных (схема v1)

- `accounts(player_uuid, last_known_name, balance_minor, status, created_at, updated_at, version)`.
  Статусы: `ACTIVE`, `FROZEN`, `SYSTEM`. `balance_minor >= 0`.
- `transactions(transaction_id, transaction_type, source_uuid, target_uuid, amount_minor,
  created_at, actor_uuid, reason, idempotency_key, metadata_json, source_balance_after,
  target_balance_after)`. Уникальный частичный индекс по `idempotency_key`.
  `amount_minor > 0`; источник или получатель — UUID игрока.
- `escrow(reference_id, owner_uuid, amount_minor, state, created_at, updated_at, metadata_json)`.
  Состояния: `RESERVED`, `CAPTURED`, `RELEASED`.
- `player_activity`, `claimed_milestones`, `weekly_payouts` — зарезервированы под этапы
  активности/недельного фонда (создаются, но пока не используются).
- `meta(key, value)` — служебные флаги (например, `legacy_import_done`).

Казна — системный аккаунт с фиксированным UUID
`00000000-0000-0000-0000-000000000001`, статус `SYSTEM`, сидируется миграцией v1.
Прямые денежные операции с казной запрещены в командах.

## 4. Денежные потоки

- `deposit(player, amount, ctx)` — плюс на баланс, запись журнала.
- `withdraw(player, amount, ctx)` — минус, требует достаточного баланса и активности.
- `transfer(from, to, amount, ctx)` — обе стороны + журнал в одной транзакции.
  Ограничения по порядку: сумма → лимиты → идемпотентность → кулдаун → балансы.
- `setBalance(player, newBalance, ctx)` — админская корректировка; в `metadata` пишутся
  `previousBalance`/`newBalance`.
- `EscrowService` — `reserve(owner, amount, ref)` списывает в резерв (состояние `RESERVED`),
  `capture(ref, buyer)` зачисляет получателю, `release(ref)` возвращает владельцу.
  Одна ссылка используется один раз.

## 5. Форматирование и ввод

- `decimalPlaces` — число знаков после запятой при отображении (0–10).
  `displayDivisor = 10^decimalPlaces`; `format(minor)` делит на делитель и показывает
  целую и дробную часть (без `double`).
- `CurrencyParser.parse(input, decimalPlaces)` разбирает ввод игрока/админа в минимальные
  единицы с контролем переполнения `long`.

## 6. Безопасность и ограничения

- Права команд: пользовательские — уровень 0, админские — уровень 4.
- Максимальный баланс (`maximumBalance`) и лимит перевода (`maximumAmount`) проверяются
  до изменения баланса.
- Кулдаун переводов хранится в памяти сервиса; при перезапуске сбрасывается
  (повторная идемпотентная операция не пройдёт благодаря ключу).
- Отключённые переводы (`transfers.enabled=false`) и офлайн-получатели управляются
  конфигом.

## 7. Отложенное / на заметку

- Этапы «активность», «милстоуны», «недельный фонд» — схема готова, бизнес-логика не написана.
- FTB/TFG-интеграции не добавлены (файлов модпака в проекте нет); интеграция делается
  через публичный `EconomyApi`.
- Один поток для БД — достаточно при серверном моде; при необходимости масштабирования
  добавить пул соединений с WAL.
